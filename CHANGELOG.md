# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- **Posters in the Match picker** — while Posters show, `t` opens the Match picker as a wide dialog of up to three tiles side by side: the current Match, the Provider's next Candidate and "Type a title". Each Candidate's tile shows its Poster, with its name, its year and its key under it; a Candidate with no Poster, a failed download or a file that cannot be drawn shows the name and "no poster", and the failure logs one line. A Poster already in the poster store is drawn at once; any other is downloaded when its tile is shown, off the screen's thread. The "Type a title" tile holds the typing field. `←` `→` move between the tiles (`↑` `↓` too), and `1` to `3`, `enter`, `/` and `Esc` work as in the list. A typed search replaces the tiles' Candidates and their Posters, and a Poster that arrives for a Candidate no longer shown is not drawn. The dialog keeps to the right of the poster panel and fits a screen of 100 columns by 35 rows; while it is open the panel shows the Title's name in place of the image, and the image returns when it closes. With Posters hidden or unavailable, or a screen below 100 columns by 35 rows, the picker is the plain list, and it changes between the two when the screen is resized while it is open ([#30](https://github.com/eunai/TermRenamer/issues/30)).
- **Posters** — with the optional `posters` extra installed (`uv tool install "termrenamer[posters] @ git+https://github.com/eunai/TermRenamer"`) and a terminal that draws Sixel or Kitty images, the Plan and Preview Stages show the selected Title's Poster in a framed panel of 24 by 17 cells, with the Provider's name on its border, beside the Title list; the Preview's summary and Apply move under the list. The app checks the terminal once at start; a plain install, or a terminal that draws neither, has no Posters and no panel. `TERMRENAMER_SHOW_POSTERS` (default `true`, the usual boolean words; any other value stops the app at start-up with exit status 2) and the Show posters row in Settings turn the panel on or off, and `i` does the same for the session; when Posters are unavailable the row and `i` say why. The panel needs a screen of at least 100 columns by 35 rows; on a smaller one it is hidden, and the row, and `i` as it turns Posters on, say the size it needs. A Poster is downloaded from the Provider's image host, never during the build, when its Title is selected at the Preview, and kept for 30 days in `termrenamer/posters` under the per-user cache folder; older files are deleted at start. When that folder, or the `termrenamer` folder holding it, is a link, or lies outside the cache folder, no Poster file is read, written or deleted: every Poster shows "no poster" and one line is logged. A Title with no Poster, a failed download, or a file that cannot be drawn shows the Title's name and "no poster", and the failure logs one line. While the Apply confirm or the Match picker is open, the dialog keeps to the right of the panel, and the panel shows the Title's name in place of the image. Help shows the credits TMDB and TheTVDB ask for ([#29](https://github.com/eunai/TermRenamer/issues/29)).
- **Undo the last Apply** — on the Applied Stage, `u` opens the Undo confirm, which says how many videos and Sidecars go back, how many Stragglers go with them, how many removed folders are made again and how many folders Apply made are removed when they are left empty; `y` puts them back and `n` or `Esc` keeps the Apply. Undo works from what that Apply recorded, last move first: the folders Apply removed are made again, each file goes back to its old place, and each folder Apply made is removed when Undo leaves it empty. A folder Straggler goes back as its files, and only when nothing is at its old place: when a folder is there again, empty or not, its files stay at their new place. A file goes back only when it is still at its new place with the size and modification time Apply recorded there, and only by claiming its old name with the move itself, so nothing at the old place is ever replaced; a file that changed, is gone or whose old place is taken stays where it is, and so does a file whose old folder is now a link or a file or lies behind a link: Undo never makes a folder or puts a file back behind a link. A rename that changed only letter case is undone too; when the disk never made it, the file is counted neither as put back nor as left. A file already at its name was not moved and is not touched, and a copy Apply could not remove after a failed move is left in place and named in the Logs. After Undo the screen is at the Queue Stage with the same Sources queued, and the message line says how many files went back and how many were left; the Logs list each file left with the reason. Undo is offered once per Apply, only when the Apply moved a file, removed a folder or made one (so a failed Apply's new folders can be removed too), and not after `n` starts a new batch. The record is kept in memory only, so Undo is gone once the app quits.
- **Pick a different Match** — on the Preview, `t` opens the Match picker for the selected Title: the current Match (marked "current"), the Provider's next Candidate and "Type a title", as a plain list (as tiles while Posters show, see above). `←` `→` or `↑` `↓` and `enter`, or `1` to `3`, choose; `/` goes to typing; `Esc` closes it and nothing changes. Picking a Candidate for a film renames its files from the Candidate's title and year with no further lookup. Picking one for a show looks its files' episode titles up again from the picked show while the Title is marked "looking up"; a file whose episode that show does not have gets the status no match, `Esc` abandons the change, and a failed lookup keeps the Plan and shows the Provider's message. Typing a title and pressing `enter` searches the Provider again (a four-digit year at the end of the text is the year), and the picker lists what it found or says that nothing was found. A Title with no Match opens the picker on "No match found." and the typing field. A not recognised film opens it with its file name, without the extension, in the typing field; once given a Match it forms a Title of its own, or joins the Title that has that Match, and its Sidecars move with it. A not recognised TV file gives a message that matching it by hand is not available yet. After a pick, every new name, Name taken and the Stragglers are worked out again across the whole Plan, two Titles that now share a Match become one, with every file named from that one Match, and the selection stays on the Title. A picked Match holds for this Plan only: it is never stored in the lookup cache as the answer for the file names, so building the Plan again from the queue starts afresh.
- **Leave a file out** — on the Preview, `x` leaves the selected video out of the Plan with its Sidecars, and `x` again puts it back; the button beside the details reads Leave out or Put back. A left out file keeps its name and stays in its folder: Apply does not touch it, and the Apply confirm, the Applied Stage and the Logs report it as left out, not as skipped. Each change makes a new Plan without asking the Provider again: every new name is worked out again in source-path order and tested on disk again, so a name that only the left out file had taken is free for the next file, and a file put back gets the status a fresh Plan would give it. The selection stays on the same file. A Title is marked left out when every file of it is; the cell, the footer (which shows the new name it would have, struck through) and the summary show the change. Any video can be left out, one with no match or not recognised too, and it stays left out when its Title is given a Match, until `x` puts it back.
- **The Preview in full** — beside the Title list, a column shows the selected Title: its name, its status, its year (Film) or number of seasons (TV), its count of videos and, when its videos differ, how many have each status. Under it, each video is a cell in its status colour, grouped by season in TV Mode; `←` `→` select a file of the Title, and the column scrolls to keep the selected file's cell in view. The footer shows the selected file's current path and new path, how many of its Sidecars move with it, and, for a file that will not be renamed, why (no match, not recognised, name taken under `skip`, or already has its name). A summary counts the videos that are ready, name taken, no match, not recognised and left out. In a terminal wider than 120 columns the Title list takes the extra space.
- **The Apply confirm says what Apply will do** — how many videos are renamed and under which folder, how many are skipped and for which statuses, how many already have their names, and that nothing has been renamed yet.
- **The Applied Stage lists what was not renamed** — after the counts, each skipped and each failed video with its reason, and each Sidecar that was not renamed while its video was. Every result, Sidecars included, is in the Logs.
- **Name taken setting** — `TERMRENAMER_NAME_TAKEN` decides what a plan does with a file whose new name is already used, by a file, folder or link at that path or by an earlier file of the same plan in source-path order: `suffix` (the default, the numbered names of before, such as ` (1)`) or `skip`, which leaves the file where it is; any other value stops the app at start-up with exit status 2. Under `skip` the file is marked "name taken", gets no new name and claims none, and Apply skips it with the reason "name taken", together with its Sidecars; a Sidecar whose own name is taken is skipped alone while its video moves. The Settings form has a Name taken row; changing it while a Plan is shown discards the Plan and keeps the queue. The Preview's footer says what will happen to the selected file when its name is taken, and the Apply confirm and the Applied Stage list each Sidecar skipped while its video moves; the Applied Stage also lists each skipped video with its reason ([#6](https://github.com/eunai/TermRenamer/issues/6)).
- **Lookup progress and cancel** — while the Plan is built, the Plan Stage lists each Title as waiting, looking up, found or no match with its count of videos, says how many files of the total are looked up, and shows a strip with the lookup gauge, the matched and unmatched counts as bars and the lookups per second. A Title can be selected during the build to see its name, status and videos. `Esc` at the Plan Stage cancels the build: no Plan is made, the queue is kept, the Queue Stage is shown, Settings, Mode and Provider can be changed again, and the message line says that nothing was renamed. A lookup already sent when `Esc` is pressed finishes, and no other starts.
- **Theme** — the screen has a dark and a light theme in teal. `TERMRENAMER_THEME` takes `dark` (the default) or `light`; any other value stops the app at start-up with exit status 2. The Theme row in Settings switches between them for the session, and switching discards nothing.
- **Duplicate Sources are refused** — adding a file or folder whose resolved path is already queued, compared without regard to letter case, is refused with a message. A folder and a file inside it can both be queued: the file is planned once, under the outermost queued folder. When the Plan is built, a queued file or folder that no longer exists, and a queued file that is not a video, are reported in the log and the rest of the queue is planned.
- **Not recognised videos are listed** — a video whose name the app cannot read is now in the Plan, marked "not recognised", with its Sidecars; Apply leaves them where they are. Before, they were left out of the Plan without a word.
- **Contributor tooling: CI** — a GitHub Actions workflow (`.github/workflows/ci.yml`) runs `uv sync --locked`, then `uv run pytest -v --cov`, `uv run ruff check .`, `uv run ruff format --check .` and `uv run mypy src`, each as its own step, on Linux and Windows with Python 3.13, each once without and once with the `posters` extra (one job per system and install, and a failure in one does not stop the others), for each pull request and each push to `main`.

### Changed

- **A move with no hard link is a checked copy** — outside Windows, Apply moves a file by giving it a hard link at its new name and then removing the old name. Where no hard link can be made, on another drive or on a filesystem without hard links (exFAT, many network shares), Apply copies the file to its new name and then removes the old one, which takes as long as a copy. On exFAT and such shares this is new: before, a move on the same drive was a rename. On Windows a move on the same drive is still a rename, and one to another drive is copied as here. The copy creates the new name exclusively, so it never writes over anything there, and it is checked against the original before the original is removed. On Windows the copy is written under a temporary name beginning `.termrenamer-` in the new folder and then renamed to its new name, which Windows refuses when anything is there, a link included. If the original changed during the copy, the file fails and the original stays; the copy is removed when possible, and when it cannot be, the Logs name it. A new name, a copy or a hard link, is removed again only while the original is still at its old name, by a look at the old name that is the last step before the removal, so a file whose old name another program removed or replaced during its move keeps its new one; and the old name is removed only while it still holds the original, so a file another program puts there during a move is never removed. Once a copy begins, a file another program puts at the old name is never taken for the original, even when the disk gives it the original's file number, as ext4 and tmpfs on Linux do with a file just removed: Apply holds the original open from the start of its copy until its old name is removed, so no other file can be given its number; on Windows, where it is held until just before, no other program can remove it meanwhile. A symbolic link is made again with its target text unchanged; on Windows, a link to a file whose target names a folder at its new place, where Windows would make it a link to a folder, fails and stays. A pipe, socket or device is never copied: it fails with a reason.
- **Stragglers are listed in the Plan** — with Folder rename on, the Plan now lists the Stragglers it will merge: the files and folders left in a source folder that a video moves out of, when that folder is a queued folder or lies inside one. A folder that holds a file of the Plan, or that is, holds or lies inside a folder the Plan moves files into, stays where it is. Each Straggler's path in its target folder is fixed when the Plan is built, and a taken path gets a number whatever Name taken says, so two Stragglers never share a path: the `folder.jpg` of two discs of one season become `folder.jpg` and `folder (1).jpg`. Two names that differ only in letter case or in Unicode form (a composed or decomposed `é`) count as one path, for Stragglers and for every other planned name. A folder Straggler is moved as its files: its folder is made again at its new place, each file is moved into it, and the emptied folder is removed. The Preview's summary and the Apply confirm say how many Stragglers merge, and the Applied Stage how many merged; it lists each Straggler not merged with the reason, and a Straggler that failed to move means the Applied Stage no longer says that nothing failed. Apply moves a listed Straggler only when a file of its folder moved to another folder in that Apply and the Straggler is still there, as a file or as a folder as the Plan listed it, and skips it with "destination exists at apply time" when something has taken its path since. Apply moves no file or folder of a source folder that the Plan does not list, such as a file added to the folder after the Plan was built; a folder Straggler is moved with what it holds when Apply runs. A video with no match and one whose name cannot be read are no longer merged as Stragglers, and neither is one skipped because its name is taken: each stays in its folder, with its Sidecars. Before, Apply merged an unmatched video into the new folder of the show beside it.
- **BREAKING: one screen in four Stages, and new keys** — the screen now walks a batch through the Queue, Plan, Preview and Applied Stages, with a header (Mode, Provider, Destination root), a row of the Stages and a footer that shows a message and the keys that work at the current Stage. The Title list fills in while the Plan is built; the Preview shows one row per Title with its status and its count of videos, and a not recognised video as a row of its own; `Enter` opens the Apply confirm, where `y` or `Enter` applies and `n` or `Esc` goes back. The keys changed: `Ctrl+F` and the folder-or-file picker are replaced by `a` (add a file) and `f` (add a folder), which open the file and folder dialogs directly; `Ctrl+,` is replaced by `s` (Settings); `F1` by `?` (Help, which lists every key); `q` quits from anywhere but a text field (`Ctrl+Q` still quits), so `Esc`, not `q`, now closes Help and Settings; `a`, which switched the Activity and Logs tabs, now adds a file, and `l` opens the Logs. New: `c` clears the queue, `Esc` at the Preview discards the Plan, `n` at the Applied Stage starts a new batch. Sources are added or cleared only at the Queue Stage; `m` and `p` work at the Queue and Preview Stages. Settings is one form: TV Destination root, Film Destination root, Folder rename, Season folder, Name taken and Theme. Season folder cannot be turned on while Folder rename is off, and turning Folder rename off turns it off.
- **A Provider failure stops the build** — when the Provider cannot be reached, rejects the key or gives an unusable answer, building the Plan stops with the Provider's message, no Plan is made and the queue is kept. Before, the files were planned as unmatched.
- **A changed setting discards the Plan** — changing a Destination root, Folder rename, Season folder or Name taken in Settings while a Plan is shown discards the Plan, keeps the queue and says so on the message line and in the Logs; changing Mode or Provider does the same. While a Plan is being built or applied, Settings, Mode and Provider cannot be changed, and the key says so.
- **Sidecars follow their video** — Apply handles each video before its Sidecars, and moves a Sidecar only when its video was renamed or already had its name; otherwise the Sidecar is skipped with "video not applied", or with its video's status ("no match", "not recognised", or "name taken" under Name taken `skip`) when the video has no name to take. A file that already has its name is reported as unchanged, and Apply's summary line counts renamed, unchanged, skipped and failed files. A planned name that was taken and got a number is marked "name taken" in the preview.
- **OMDb searches by title** — a Film plan with OMDb now uses OMDb's search and takes the first film it lists that has a year, as TMDB does. When OMDb answers that a search has too many results, the app asks OMDb for the single title instead, as it did before.
- **Any one provider key is enough to start** — the app starts when at least one of `TERMRENAMER_TMDB_API_KEY`, `TERMRENAMER_TVDB_API_KEY` and `TERMRENAMER_OMDB_API_KEY` is set; it no longer requires the TMDB key (#3). With none, it exits with status 2 and a message that names the three settings, says one is enough and says where to set them; a TheTVDB subscriber PIN alone is not a key. At start and on every change of Mode the provider is the first of that Mode with a key (TMDB, then the other), or TMDB when none has one. A provider with no key is marked "no key" and `p` still selects it; building a plan with it, TMDB included, names the setting to add and builds no plan.
- **Contributor tooling: coverage check** — the full test check is now `uv run pytest -v --cov` (was `uv run pytest -v`). Coverage is no longer in pytest's default options, so `uv run pytest` with a single test file runs those tests only and exits 0 when they pass, where it used to fail on the 85% coverage threshold. `--cov` measures `src/termrenamer` and still fails below 85%, from `[tool.coverage]` in `pyproject.toml`.

### Removed

- **The Activity tab** and its match events; the log lines are in the Logs view (`l`).
- **The folder-or-file picker** opened by `Ctrl+F`; `a` and `f` open the file and folder dialogs directly.
- **The gruvbox theme**; the screen uses its own dark and light themes.

### Fixed

- **The footer lists the keys that work, by one rule** — when the key hints do not all fit, the footer drops them in a stated order: Poster, Logs, Provider, Mode, Settings and Quit first, then the selection keys, then the Stage's own keys from the last. `? Help` is never dropped; before, the last hints were cut, Help among them, even at 120 columns. While an Apply or an Undo runs, the footer no longer lists the keys that refuse meanwhile, such as Apply, Match, Leave out, Settings and New batch.
- **A path with an unknown user no longer stops the app** — a Destination root typed in Settings as `~someone/TV`, for a user the system does not know, is refused with a message and the root set before is kept. The same value in `TERMRENAMER_TV_DEST_FOLDER`, `TERMRENAMER_FILM_DEST_FOLDER`, `TERMRENAMER_CACHE_DB_PATH` or `TERMRENAMER_LOG_FILE` stops the start with exit status 2 and a message naming the variable, as an invalid value does.
- **Odd Provider answers** — a TheTVDB episode list answer that holds no list fails the lookup with the Provider's message, where it counted as nothing found; a year, show id or episode number written with digits other than 0 to 9 (such as `²000`) counts as missing, so a film Candidate, a show with such an id or such an episode is dropped and a show keeps no year, where the build stopped on an unexpected error.
- **Each file is planned under its own path** — on a disk that tells letter case apart, two folders of one queued folder whose names differ only in letter case, such as `Disc` and `disc`, now keep all their videos, and a Sidecar pairs only with a video in its own folder; before, one of two videos with the same name was dropped from the Plan. A queued file reached under another spelling of a queued folder, in letter case or Unicode form, is planned once, spelled as the disk lists it. A queued video that is a symbolic link is planned and renamed as the link, at its own name and folder; before, its target was renamed. Planning never enters a symbolic link or a Windows junction to a folder inside a queued folder, so no video behind it is planned; a queued folder that has become such a link since it was queued is reported in the log and skipped. A file that already has its name keeps it, and is reported as unchanged, when the queued folder or the Destination root is typed in another letter case than the disk lists it. Two planned names that reach one path through a folder link at the destination, or that are one name once letter case is set aside and combining marks are put in order, count as one path: the second is name taken. Under Name taken `skip`, a name is either the planned one or none, even when a file appears at it while the Plan is built. A folder whose name differs from its new folder's only in letter case is that folder on a disk that ignores letter case, so its files are not moved into it as Stragglers, and another folder on a disk that tells letter case apart, so its Stragglers go along and it is removed once empty.
- **Paths and names are shown as they are** — a path, a file or folder name, a Provider's name and an error message are no longer read as markup on the screen. A name with square brackets, such as `[Group] Show`, keeps them; before, some were dropped. On Windows a folder's closing backslash no longer puts a `[/]` after the folder in the Applied Stage and the header, nor a second backslash in the Apply confirm. The file and folder dialogs show their current folder as written too.
- **Apply never replaces a file that appears while it runs** — Apply claims each new name with the move itself, so a file or folder that appears at that name while Apply runs is never replaced: the file or Straggler is skipped with "destination exists at apply time". This holds for videos, Sidecars and Stragglers, on every system and every kind of drive. Before, something that appeared at the name in the moment before the move could be overwritten, and a folder Straggler could be moved into a folder that had appeared at its name. A separate hard link of the same file at the new name now counts as taken; before, Apply reported it renamed while both names stayed. A symbolic link or a Windows junction to a folder is moved as itself and never entered, so nothing behind it is moved; a junction that would have to go to another drive fails instead. A video that is a link, found inside a queued folder, is renamed as the link. Apply moves nothing through a folder that has become a link or a junction since the Plan was built, the Destination root or a folder on the way to a new name, a source folder or a folder Straggler: the file or Straggler is skipped with "the folder … is now a link", or fails with that reason when part of a folder Straggler had moved. A Destination root or a folder on the way to a new name that was a link when the Plan was built is gone through only while it is the same link, with the same target, leading to the same folder: one pointed elsewhere or removed since is skipped with "the folder … is no longer the link the Plan found", and no folder is made in its place. Changing a Match or leaving a video out and putting it back never reads such a folder again, so a link made after the Preview is not taken for one the Plan found, under any letter case. A file that changed since the Plan was built is skipped with "stale: source changed since plan", also when it changes while Apply makes its new folder, and a link is checked as itself, not by its target.
- **The files beside a queued file stay where they are** — with Folder rename on, applying a Plan of a single queued file no longer moves the other files and folders of its folder into the file's new folder. Only folders that were queued, and the folders inside them, have Stragglers.
- **The file and folder dialogs no longer stop the app** — the file and folder dialogs list their folder in the background. A listing that read its colours while the screen was redrawing it could stop the app with a `KeyError` about `directory-navigation`. It now reads them on the screen's own thread, so opening, browsing or closing either dialog at any moment is safe. A folder that is gone, cannot be read or cannot be entered by the time a dialog lists it leaves the dialog open with a line that says why and nothing listed but `..` (not even that when the folder above cannot be looked at either), and the queue as it was. A path typed in the file dialog that the disk cannot look at gets no suggestion, where it ended the app.
- **Apply uses the Plan's Folder rename** — Apply merges Stragglers by the Folder rename value the Plan was built with, not by the current setting.
- **Stragglers leave the Plan's files and target folders alone** — merging Stragglers no longer moves a file of the Plan that Apply skipped, such as a video changed since the Plan was built, nor a folder that is, holds or lies inside a folder the Plan moves files into, nor a link to a folder that a new folder's path goes through. Before, a second show's new folder at the top of a queued folder could be moved into the first show's season folder.
- **Numbered names across queued folders** — when files from several queued folders want the same name, the numbers are given once across the whole Plan in source-path order, so a name such as `Title (1) (1).mkv` no longer appears.
- **OMDb lookups are cached** — with `TERMRENAMER_CACHE_DB_PATH` set, OMDb film lookups now go through the SQLite cache like TMDB and TheTVDB lookups, so a second plan of the same films sends no OMDb request ([#5](https://github.com/eunai/TermRenamer/issues/5)).
- **Cache entries kept apart by provider** — every cache entry is now stored under the provider it came from, so a lookup cached from one provider is never used for another, in TV or Film. A search that found nothing is not stored. When a film search with the filename's year finds nothing and the search without the year finds the film, both are stored, so the next plan sends no request for it. Existing cache entries are discarded once: the first plan after this update drops the old entries from the cache file, which fills again as you plan. Deleting the file is still safe.
- **Cache across plans** — a second plan built in the same session now reads what the first one stored. Before, the cache only worked for the first plan of a session, and later plans logged a cache warning and fell back to the network.
- **Broken symbolic links** — a broken symbolic link now counts as a file that is already there. A planned name held by one is taken, as any other taken name: under Name taken `suffix` the file gets the numbered name, and under `skip` it stays where it is. A Straggler's path in its target folder held by one is always numbered. If one appears at a destination after the preview, apply skips that entry or Straggler with "destination exists at apply time" instead of replacing the link ([#9](https://github.com/eunai/TermRenamer/issues/9)).

### Security

- **Provider requests no longer follow redirects** — a TMDB, TheTVDB or OMDb answer with a 3xx status fails the lookup with a message that names only the status and the host, so a key or TheTVDB's PIN never goes to the address the answer names; before, the request followed it. Poster downloads already refused redirects.
- **Provider keys no longer reach the logs** — since 0.1.0, each request to TMDB or OMDb that got an answer wrote a log line with the request's full address, which holds the TMDB key (`api_key=`) or the OMDb key (`apikey=`), and the Logs showed that line. A lookup answered from the cache sent no request. TermRenamer writes no log file, and the console takes no log lines while the screen runs. That line is no longer written. In its place, each answer the app uses is logged with the method, the host and the path of the request as the app made it, never its query string. Every line the Logs or the console write, traceback included, shows `***` in place of a Provider key or TheTVDB's login token of 8 characters or more. A secret that a server echoes back in an error, or that another library logs on its own, is masked only when it is such a key or token; TheTVDB's subscriber PIN is kept out by never being written to a log line. If you shared a screenshot of the Logs or a copy of those lines, make a new key with that Provider and set it in place of the old one.

## [0.1.0] - 2026-11-26

### Added

- **Contributor tooling: README screenshot** — `uv run python scripts/render_preview.py` regenerates `docs/assets/preview.svg`, the README's picture of a TV plan in the preview. It runs headless with stand-in metadata, so it needs no network, API key or settings file. The version check now also fails when the README's Version badge differs from the newest changelog version.
- **User settings file** — the app reads its settings from a per-user dotenv file named `.env` in a `termrenamer` folder: `%APPDATA%\termrenamer\.env` on Windows, `$XDG_CONFIG_HOME/termrenamer/.env` (or `~/.config/termrenamer/.env`) on macOS and Linux. An installed copy finds your keys whichever folder you start it from. A `.env` in the current folder overrides it, and `TERMRENAMER_*` environment variables override both; a blank value counts as not set. The app only reads this file. A missing TMDB, TheTVDB or OMDb key now prints the file's full path. See `.env.example`.
- **Layout controls** — **Settings** (**Ctrl+,**) includes a **Layout** tab: **Enable folder rename** and **Enable season folders (TV)** (season option is disabled when folder rename is off). Same options are available as `TERMRENAMER_ENABLE_FOLDER_RENAME` and `TERMRENAMER_ENABLE_SEASON_FOLDERS` (both default **false**). When folder rename is **off**, only the media **filename** changes in its current folder; TV/film **destination root** env fields are **not** used for path layout. When folder rename is **on**, roots apply as before; TV can use flat show folder or `Season NN` trees. Apply can **merge stragglers** (extra files left in the old folder) into the destination tree with the same collision rules. See README and `.env.example`.
- Initial release.

### Changed

- **Breaking: `.env` lookup** — the app reads a `.env` only from the exact folder you start it in; it no longer searches parent folders or its own source folder. Migration: start a clone from the folder that holds its `.env`, or move your keys to the user settings file.
- **Contributor tooling: uv** — development now uses [uv](https://docs.astral.sh/uv/): `uv sync` installs the app and the `dev` dependency group (moved from the `[dev]` extra, so `pip install -e ".[dev]"` no longer installs dev tools), pinned by the committed `uv.lock` and `.python-version` (3.13). Run checks with `uv run pytest -v`, `uv run ruff check .`, `uv run ruff format --check .` and `uv run mypy src`. Installing the app with `pip install .` still works without uv.
- **Default rename layout** — bootstrap defaults are **filename-only** (both layout toggles off), which differs from earlier releases that always built show/season (TV) or title (film) folder trees. Enable **folder rename** in Settings or via env to restore library-style folder output.
- **TUI — responsive planning and apply** — **Build plan** and **Confirm apply** run network and filesystem work in Textual **thread workers** (exclusive group) so the UI event loop is not blocked during metadata lookups or renames. While a worker is running, **+ file**, **+ folder**, **Plan**, **Apply**, **Clear**, and **Cancel** are disabled; the preview and the explicit confirm before any rename are unchanged.

### Removed

- **Unused dependency** — `tomli_w` is no longer installed with the app.

### Fixed

- **Installed copy starts** — the built package now includes the terminal UI's stylesheet, so `termrenamer` installed with `uv tool install` or `pip install` opens the terminal UI instead of failing at start-up.
- **Activity tab** — Activity feed lines triggered while planning runs on a worker thread are applied on the main UI thread (thread-safe for Textual `RichLog`).
- **SQLite cache** — `SqliteMetadataCache` now closes the DB handle on destruction as a backstop; explicit `close()` remains the preferred lifetime boundary.
